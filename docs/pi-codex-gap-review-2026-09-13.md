**What the source comparison establishes.** Pi already implements stable session cache keys, cached WebSocket input deltas, recovery from a missing continuation, encrypted reasoning replay, assistant message phases, and cache-read/cache-write usage accounting. Sending full history over SSE is not inherently a cache miss. Also, `previous_response_id` does not make earlier context free: previous input in the chain is still billed by the public API. [Conversation-state documentation](https://developers.openai.com/api/docs/guides/conversation-state).

Public API documentation says newer models default to a 30-minute cache lifetime. It also distinguishes cache routing from cache accounting across model generations. That does not establish identical behavior for the ChatGPT subscription endpoint. Neither the local Codex request builder nor the inspected current upstream builder emits the TTL/breakpoint fields claimed by the binary-string-based reports; finding documentation strings inside a binary is not proof of its outgoing requests. [Prompt-caching documentation](https://developers.openai.com/api/docs/guides/prompt-caching), [current Codex request construction](https://github.com/openai/codex/blob/3abbf9fe2c6b6910e9de61f6a0c5bb468f74b5c8/codex-rs/core/src/client.rs#L879), [request schema](https://github.com/openai/codex/blob/3abbf9fe2c6b6910e9de61f6a0c5bb468f74b5c8/codex-rs/codex-api/src/common.rs#L260).

Codex's concrete differences include canonical [Responses metadata](/mnt/secondary/workspace/codex/codex-rs/core/src/responses_metadata.rs), per-turn routing state, native compaction, and gated reasoning updates. Current Codex pins the original request effort within a context window and appends trusted changes; successful compaction permits a fresh baseline. This is gated on its feature flag, OpenAI provider and Responses Lite model capability, not enabled for every arbitrary Responses endpoint. [Current reasoning lifecycle](https://github.com/openai/codex/blob/3abbf9fe2c6b6910e9de61f6a0c5bb468f74b5c8/codex-rs/core/src/session/reasoning_effort.rs).

2. **Repair prefix preservation in native memory and custom wakes.** In [memory.ts](/mnt/secondary/workspace/pi-generalist-extensions/extensions/memory.ts:129), replace the per-request packet projection with durable snapshots at fixed message boundaries, using [snapshotContext](/mnt/secondary/workspace/pi-generalist-extensions/lib/workpad/context.ts:21) as the starting point. Reload should reconstruct unchanged authorized snapshots without rereading personal sources. Existing tests that require removal on ordinary reload will need to change; revocation tests must remain meaningful.

Stable personality/native-memory guidance needs a durable session contribution; changed instructions should append an update at an explicit boundary. [PR #9548](https://github.com/earendil-works/pi/pull/9548) is a useful design reference, but its 83-file prompt/tool refactor is a separate review, not part of rebasing to HEAD.

   Acceptance: capture final native-Codex and public-Responses payloads for ordinary users, tool continuations, retries, background wakes and reloads. Verify initial instructions, ordered tools and all prior input items remain identical. Use synthetic personality, native memory and reflective-continuity fixtures independently and together. Test compaction, activation changes and revocation as explicit lifecycle changes. Existing context-snapshot observations occur before provider conversion/payload hooks and are not sufficient evidence alone.

3. **Add canonical Codex identity and routing state.** Use [PR #9488](https://github.com/earendil-works/pi/pull/9488), inspected at `08fcee62635f3b6179bf131dd8f0d489d04adc64`, as a candidate implementation. Its central identity, native request projection and routing changes address real gaps. I inspected those portions; I did not apply or run that PR's reported tests. Preserve one turn ID across tool continuations, steering, transport retries, agent retries and overflow recovery. New top-level prompts/queued follow-ups get new turn IDs. Give internal summary/compaction/memory calls appropriate request kinds, and represent child-thread lineage honestly. Cache preference must not erase request identity.

   Emit the canonical body metadata plus compatible headers on HTTP requests and every WebSocket `response.create`; handshake headers alone cannot describe later turns. Capture the first server routing token for a turn and replay it only for that turn. Scope cached sockets and continuation state by normalized endpoint and account; protect cleanup and reconnect against stale asynchronous handshakes. Exclude non-model-visible attribution fields from WebSocket prefix comparison while still comparing actual model inputs/settings.

   Extend the candidate's window scheme before calling it full Codex parity: its builder uses `window_id = thread:compaction-count` and omits Codex's separate `context_window_id`/`window_number`. Two sibling branches compacted once can share the same count. Derive stable, distinct window identity from the committed checkpoint (or persist a UUID), with explicit resume/fork semantics. Acceptance must include sibling branches with equal compaction counts, failed/cancelled compactions, same-account token refresh, endpoint changes and reconnect races. Keep `originator: pi`; no client impersonation is needed. This is a protocol-correctness proposal, not a promised quota reduction.

4. **Harden the transport independently.** Port and review the narrow [#9037 parser change](https://github.com/earendil-works/pi/pull/9037), including LF/CRLF/CR boundaries split across chunks, a bounded pending event and explicit failure on oversize input. Preserve EOF flushing. Add separate body-idle and total deadlines: activity may refresh idle time but must not extend the total deadline. Distinguish timeout from user cancellation, cancel only the affected reader/socket, and bound retries/reconnects across provider and agent layers. Do not silently retry completed tool work. A configurable WebSocket re-probe after fallback is a later resilience choice, with backoff and owner checks; it is not evidence that pi's fallback alone consumes more than Codex.

5. **Fix summary request policy, then evaluate prefix reuse.** Centralize transport, timeout, authentication, identity and request-kind propagation for compaction and branch summaries. Give summarization an independent reasoning setting/output budget and one bounded recovery strategy for a truncated summary; never commit incomplete output. The public Responses cap shares room with reasoning. Native Codex's adapter does not send `max_output_tokens`, so copying a public-API cap into that endpoint is not an established solution.

   For branch summaries, evaluate a capability-gated mode that uses the frozen provider conversation prefix and appends a summary instruction. Preserve tool schemas for prefix reuse while preventing execution and rejecting tool-call output. Test whether `tool_choice: none` itself affects cache eligibility for the endpoint, and compare both summary quality and reported usage. Full structured history can cost more if it misses cache, so this should be measured before becoming the default. Keep a bounded standalone fallback.

6. **Add native context features as separate follow-ups.** First add durable, capability-gated `configuration_update` items with a pinned request effort and correct reload/compaction semantics, following the current Codex lifecycle rather than just changing request serialization. Then prototype `/responses/compact` with opaque-item persistence and exact returned-window replay. Preserve the previous context on failure, validate the compaction input fits the window, and record a new committed context epoch on success. Native compaction does not promise preservation of the entire pre-compaction prefix. Keep it independent from `store:true` response chaining. [Standalone compaction documentation](https://developers.openai.com/api/docs/guides/compaction).

   Take [#9442](https://github.com/earendil-works/pi/pull/9442) only if a Chat Completions proxy path is in use; its key-support flag is a separate concern from retention and attribution. Defer a default-TTL change and explicit-breakpoint rollout until a reproducible wire/usage comparison establishes a benefit. Do not apply the breakpoint syntax suggested in an issue without checking the actual endpoint schema.
